# ISO 20022 Mesh and Actors — Design

Sub-project 7b in `docs/expansion-roadmap.md`, the second of three that replace
the repository's largest remaining payments fiction:

> **No ISO 20022 message parsing.** The `Payment` struct stands in for
> `pain.001`/`pacs.008`/`pacs.003`; the schemes only *name* the messages they
> correspond to. (`README.md:1016`, `payment/doc.go:61`)

7a shipped the vocabulary — four messages, the `head.001` header, the
`<Envelope>` wrapper, the codec, the external code sets — in a package that
imports nothing from this repository and is imported by nothing in it. This
sub-project is what gives it a consumer, and what makes those two bullets false.

- **7a — the `iso20022` package.** Done, 31 commits on `spec/iso20022-messages`.
  Spec: [`2026-07-31-iso20022-messages-design.md`](2026-07-31-iso20022-messages-design.md).
- **7b — this spec, the mesh and the actors.** One goroutine per entity
  exchanging marshalled bytes; the creditor-side check leaving
  `InitiatePaymentTx` and coming back as a `pacs.002`; `api/` becoming
  genuinely asynchronous.
- **7c — the message log.** Envelopes persisted in both stores so a payment
  screen can show the XML that actually moved, plus `README.md`,
  `hint-content.ts` and the quiz.

## Goal

Make the message the interface between banks, rather than a function call
between two halves of one process that happen to be named after banks.

Concretely: after 7b, a bank cannot learn whether a payment was accepted except
by receiving a `pacs.002` saying so. That single constraint is what converts
clearing from a synchronous validation into a conversation, and it is the whole
subject.

## What was decided before writing this

Five questions were settled in the brainstorming session, three of them against
what the roadmap says. Each is argued in full below; collected here so a reader
knows what changed:

1. **Channels, not sockets.** The mesh is one process. `-entity` is removed.
2. **Hub-and-spoke via the clearing house.** A bank never addresses another bank.
3. **The central bank is an actor, and gains a fifth message** —
   `pacs.009.001.08`, which 7a did not ship.
4. **Closing a cycle emits the settlement instruction.** The central bank's
   `POST /settlements` is deleted.
5. **Sub-project 8 stays after 7b**, with two additions to 7b that make it a
   mechanical extraction rather than a redesign.

## The transport: channels, and the roadmap's argument is backwards

The roadmap states:

> Go channels do not cross process boundaries, so the mesh lives inside one
> binary running every listener — 6a's default. It therefore uses channels
> directly rather than behind a transport interface. (lines 342–347)

That reasons from the transport to the topology. 6a already settled the
topology — the deployment unit is the listener, not the process — so the
topology constrains the transport, not the reverse. And the roadmap's
consequence, that "7b must either refuse `-entity` or carry a second transport"
(line 350), is a false dilemma: a third option is to carry only the transport
that works in both modes, which is HTTP, since every listener is bound on
localhost anyway and a POST does not care whether the target shares its process.

The decision is nonetheless **channels**, and the reason is a scope decision
rather than a technical one: this system is to run in one process. Multiple
processes are not wanted, so the capability HTTP would preserve is a capability
nobody will use, and paying for real I/O — timeouts, retries, partial writes,
a slower and flakier test suite — to preserve it would be paying for nothing.

What that costs, stated so it is not discovered:

- **"The counterparty is down" is not expressible.** A send to a live actor
  always succeeds. `RC01` remains reachable, because a BIC can fail to resolve
  against the routing table; a timeout does not.
- **Delivery is exactly-once and in order**, which is a property of an
  in-process queue and not of a payment network. The package doc says so, so a
  reader does not infer that clearing is reliable by nature.

To keep the decision reversible without paying for an abstraction that has one
implementor today, **all sending goes through a single unexported function**.
Not a `Transport` interface — one function, one place. Swapping it for an HTTP
POST later is a contained change; the roadmap's objection to a one-implementor
interface stands, and this is what answers it.

### `-entity` is removed

`-entity` runs one entity per process and is the only flag that exists solely
for the multi-process topology. With an in-process mesh it would start a
listener that serves its API and can neither send nor receive a message —
payments hanging with no explanation, far from the cause.

Removed: the flag (`cmd/server/main.go:56`), `checkEntityMode`,
`resolveEntities`, `selectEntity`, `slugify`, `foldAccent` and their tests
(`cmd/server/listeners.go`), and `make dev-split`. `plan`, `serve`, `handlerFor`
and the `entity` type stay — they are the listener table, which the default mode
uses.

6a's spec called the DSN refusal "a refusal worth more as teaching than the
split itself", and the reasoning survives the flag: a shared store is what makes
one process necessary. It stays in `README.md` as prose rather than as a
runnable mode.

## The actors

One `mesh.Mesh` owning N+2 actors: one per member bank, one clearing house, one
central bank.

```
api/  ->  mesh/  ->  payment/  ->  iso20022/
                          |            ^
                          '- translate '
```

`mesh` imports `payment` and `iso20022`. `payment` gains an import of
`iso20022` for `payment/translate.go`. `iso20022` continues to import nothing
from this repository, and 7a's `imports_test.go` continues to pin that.

The mesh lives in its own package rather than inside `payment` because
`payment/system.go` is already ~1,600 lines and would otherwise hold the domain,
the transport and the concurrency layer at once.

```
mesh/
  mesh.go        Mesh, Start, Stop, Drain, send, routing
  queue.go       the unbounded inbox
  bank.go        a member bank's handlers
  csm.go         the clearing house's handlers
  centralbank.go the settlement agent's handlers
  ops.go         the narrowed per-actor interfaces
```

### Queues are unbounded, not buffered channels

A fixed-size buffer between two actors that message each other is a deadlock,
and here they do: the CSM sends to a bank while that bank is sending to the CSM.
An unbounded queue means a send never blocks, so no cycle can wedge.

A mutex, a slice, and a one-slot signal channel. Queue depth becomes readable,
which is a thing a real CSM has and a `chan []byte` does not.

### `send` is the single choke point, and it passes bytes

```go
func (m *Mesh) send(from, to iso20022.BIC, env iso20022.Envelope) error
```

It calls `iso20022.Marshal` and enqueues the resulting `[]byte`; the receiving
actor calls `iso20022.Unmarshal`. **Structs never cross.** This is 7a's stated
contract:

> If two actors exchanged `*Pacs008` the message format would be decoration on a
> function call, malformed input would stop being a reachable failure mode, and
> the `FF01` rejection path would be untestable.
> (`2026-07-31-iso20022-messages-design.md`, line 171)

A `to` that resolves to no actor is `RC01`, returned as an error the caller
turns into a rejection — not a nil map read.

Note the consequence 7a flagged and this spec accepts deliberately: `Unmarshal`
validates, so a structurally-fine message carrying a malformed BIC is *rejected
at the receive boundary* rather than answered with a `pacs.002`. That is the
right place for it. A malformed BIC is a framing failure, not a business
rejection, and `FF01` (InvalidFileFormat) is what the code set has for it.

### Routing is by `BICFI`

`map[iso20022.BIC]*actor`, built at `Start` from the participant roster plus two
configured institution BICs.

- **`Participant.BIC`** is a new field, validated with `iso20022.BIC`. This is
  the cost 7a's spec booked to 7b (line 449) and it is not zero: `store/mem`, a
  `bic` column in `store/pg/schema/0001_init.sql` with a `COMMENT ON COLUMN`,
  `participantColumns` (`store/pg/tx_payment.go:85`), a `store/storetest` case,
  seed values, and the participant DTO.
- The clearing house and the central bank have no store row, so their BICs are
  constants in `mesh`. Without them a `head.001` `Fr`/`To` would be meaningful
  for the banks and invented for the institutions, which is exactly the kind of
  half-modelled thing this repository tries not to ship.

The CSM is **one** goroutine, so mutation of the open cycle serializes without a
lock.

### `Drain` — quiescence, and it reports what was swallowed

```go
func (m *Mesh) Drain(ctx context.Context) error
```

An in-flight counter is incremented **before** enqueue and decremented only
after the handler that consumed the message has returned. A message that begets
messages therefore keeps the count above zero, and `Drain` blocks until it
reaches zero. No sleeps, no polling, no deadline on the happy path.

This is the single mechanism that keeps an asynchronous system testable without
flakiness, and it is used by more than the tests:

- The **seed** drains before `cmd/server` logs `listening`, so `make dev` never
  presents a half-processed payment.
- **`/admin/reset`** drains before truncating.
- **Shutdown** drains, then stops.

An actor handler has nobody to return an error to. Where the inbound message
admits an answer, a handler error becomes a `pacs.002 RJCT` with the mapped
reason code. Where it does not, it lands in a **dead-letter list**, and `Drain`
returns those errors joined.

That last clause is deliberate. Every test that drains therefore asserts that
nothing was silently eaten. This repository has recorded three separate
incidents of confidently-worded prose asserting behaviour the code did not have;
an actor that swallows handler errors is the same failure with a concurrency
wrapper on it.

`Drain` taking a `ctx` is what turns a wedged handler into a timeout that names
the actor and the message, rather than `panic: test timed out after 10m`.

## The choreography

### The rule that replaces "the creditor check moves"

The roadmap says the creditor-account check moves out of `InitiatePaymentTx`
(line 328). That is true for a credit transfer and backwards for a direct debit.
The rule that covers both:

> `InitiatePaymentTx` splits into a **debtor bank's half** and a **creditor
> bank's half**. Which one runs at submission depends on `Scheme.Direction()`.

- **Debtor bank's half** — debtor account exists, is open, is in the scheme's
  asset, is addressable in the scheme's identifier scheme; funds are available;
  post the debtor leg.
- **Creditor bank's half** — creditor account exists, is open, is in the
  scheme's asset, is addressable.

For a **push** (SCT) the debtor's bank submits, so its half runs first. For a
**pull** (SDD) the *creditor's* bank submits, so its half runs first and
**nothing is posted at submission** — the debtor leg is posted by the debtor's
bank when it accepts the collection, which is the only moment either the funds
or the account are in view.

This exposes a real defect. `api/handlers_bank_payment.go:86` requires
`dom.Debtor.Participant == s.boundPID` on every submission — the wrong bank for
a direct debit, which a creditor's bank submits. The check becomes
direction-aware. It was invisible before because the same process validated both
ends regardless of who called.

`SDD.Validate` (`payment/scheme.go:143`) splits along the same seam, and along
who holds what in SEPA: the **creditor's bank** validates the mandate, because
it holds the mandate, synchronously at submission (`MD01`, `MS03` as a 422); the
**debtor's bank** validates funds on receipt, asynchronously (`AM04` as an
`RJCT`).

`Initiated` becomes an observable state for the first time. Today
`InitiatePaymentTx` transitions straight to `Accepted` (`payment/system.go:1126`)
inside the submitting transaction, so no caller has ever seen `Initiated`. The
existing transition table already permits exactly what the mesh needs
(`Initiated: {Accepted, Rejected}`, `system.go:1371`); nothing about
`PaymentStatus` changes.

Adding the payment to the open cycle moves from the submitting bank to the CSM,
where clearing belongs. A consequence worth naming: `ErrCycleNotOpen` stops
being a 422 at submission and becomes an `RJCT`/`TM01` from the CSM — which is
what `InvalidCutOffTime` actually means.

### A — SCT, the push

```
customer -POST /payments-> [debtor bank]
    debtor half: checks, posts the debtor leg, status Initiated, no cycle
        --pacs.008--> [CSM]
            resolve CdtrAgt BICFI      else RJCT/RC01
            open cycle for the scheme? else RJCT/TM01
                --pacs.008--> [creditor bank]
                    creditor half      else RJCT/AC01|AC04|RR01
                <--pacs.002 ACCP|RJCT--
            ACCP: transition Accepted, add to the open cycle
            RJCT: transition Rejected, record the code
        <--pacs.002--
    on RJCT: reverse the debtor leg
```

### B — SDD, the pull

The same skeleton with the roles swapped:

```
creditor -POST /payments-> [creditor bank]
    creditor half + mandate checks; nothing posted
        --pacs.003--> [CSM] --pacs.003--> [debtor bank]
                                 funds check   else RJCT/AM04
                                 post the debtor leg
                             <--pacs.002 ACCP|RJCT--
```

`MndtRltdInf.MndtId` carries `Payment.MandateID`, which makes the mandate travel
with the collection rather than remain a foreign key the network happens to
hold.

**`MndtRltdInf.DtOfSgntr` maps `Mandate.CreatedAt`**, documented in
`translate.go`. This closes one of the two questions 7a left open
(`2026-07-31-iso20022-messages-design.md`, line 471). A `SignedAt` field was
considered and rejected: in this system a mandate is created at the moment it is
authorised, so the two are the same fact, and a second column would be a field
with no independent source — the shape sub-project 1 already removed once when
it deleted the runtime `assets` table.

### C — Reject, and the first operation that can half-happen

`RejectPaymentTx` (`payment/system.go:1156`) today does three things in one
`Store.Update`: reverses the debtor leg (the debtor bank's book), removes the
payment from its cycle (the CSM's), and transitions and audits it (the CSM's).
Under the mesh those are two units of work in two actors — the CSM transitions
and drops from the cycle, the debtor's bank reverses its leg on receiving the
`pacs.002`.

**This is the first operation in this repository that can half-happen**, and it
is named here rather than discovered: if the reversal fails, the payment is
`Rejected` with the customer's money still sitting in clearing suspense.

It surfaces as a dead letter, so `Drain` fails the test rather than the system
lying about it. Making it genuinely atomic requires the unreconciled-position
concept the roadmap assigns to sub-project 8. 7b's job is to expose the seam
honestly, not to close it — and this is the same lesson 8's roadmap entry
already states in the opposite direction: settlement is final, and a bank's
mirroring of it is not.

### D — Return, the `pacs.004`

> Written before Task 16 and kept as the design record: every present-tense
> claim about `ReturnPaymentTx` below — that it moves reserves, that all three
> compensating postings commit together or not at all, and the `(atomic)` in the
> diagram — describes the code as it stood then, and that function was deleted at
> Task 16e, whose shape `mesh/doc.go`'s "# The return" records instead.

Routed to the **central bank**, not the CSM. `ReturnPaymentTx`
(`payment/system.go:1210`) moves reserves, and its own doc comment says all
three compensating postings — debtor's bank, creditor's bank, central bank —
commit together or not at all. The actor that owns reserve movement is the
settlement agent, and `payment/doc.go` already records that returns settle
immediately rather than through a later R-cycle, so a return genuinely *is* a
settlement act here.

```
[creditor bank] --pacs.004--> [CSM] --pacs.004--> [central bank]
                                                     ReturnPaymentTx (atomic)
[debtor bank] <--pacs.004-- [CSM] <--pacs.002 ACSC--'
```

`ReturnPaymentTx` itself is unchanged. Splitting it is 8's.

### E — Settlement, and the fifth message

Roadmap line 317 says the central bank becomes an actor. 7a shipped four
messages and **none of them is a settlement instruction** — the real one is
`pacs.009` (FinancialInstitutionCreditTransfer), and settlement notification to
banks is `camt.054`, both out of scope across all of sub-project 7. So the
central bank as written had nothing it could send or receive.

7b ships **`pacs.009.001.08`** in `iso20022`, and reuses the existing `pacs.002`
for the answer. One new message type buys a full request/response:

```
POST /cycles/{cid}/close   (clearing house)
    CloseCycleTx: net positions computed, payments -> Cleared
    --pacs.009--> [central bank]        one message per asset;
                     SettleCycleTx       CdtTrfTxInf[] = one leg per bank
                     (one atomic Store.Update — unchanged)
    <--pacs.002 ACSC | RJCT/AM04--
    --pacs.002 ACSC--> each bank, per payment
```

`CdtTrfTxInf` being a slice is the message's actual cardinality, and a net
settlement is exactly the bulk it was shaped for — one leg per participant, in
one instruction. This is the first place in the repository where 7a's decision
to keep the slice pays off.

**A net payer who cannot cover their position becomes `RJCT`/`AM04` on the
settlement instruction.** That is a better model than today's behaviour, where
`SettleCycle` returns an error to whoever called it and the failure is a Go
error rather than a message the CSM can act on.

**Closing the cycle emits the instruction.** There is no separate settle button
anywhere. This is the real shape — cutoff, then the file goes — and it removes a
step that existed only because settlement was a function call.

The central bank's `POST /settlements` is therefore **deleted**. `GET /reserves`,
`GET /reserves/{pid}` and the settlement reads stay. This looks like a reversal
of 6a, which deliberately moved settlement onto the central bank on the grounds
that "a clearing house that could do that would be a central bank" — but it is
that principle applied more exactly. The CSM **instructs**; the central bank
**decides and posts**, and can refuse. Under 6a the clearing house could not
settle because it had no route; under 7b it cannot settle because it does not
hold the reserves, which is the real reason.

Settlement stays one atomic `Store.Update` at the central bank. That is what a
settlement agent is, and distributing it is not a smaller version of sub-project
8 — it is sub-project 8.

## Enforcing the boundary rather than trusting it

With one shared store, a handler that reads another entity's books compiles and
every test passes. 7b could ship with hidden cross-reads that sub-project 8 then
discovers all at once. "The boundary is a convention" is precisely the kind of
claim this repository has been burned by, so two mechanisms make it enforcement:

**Narrowed per-actor interfaces.** Each actor holds not `*payment.Network` but a
small interface — `bankOps`, `csmOps`, `settlementOps` — all satisfied by
`*payment.Network` today. A bank handler that calls `SettleCycleTx` does not
compile. Cheap now, and it is 8's seam drawn a sub-project early.

**A book-access recorder in tests.** Every `ledger.Tx` method takes
`book BookID` as its first argument (`ledger/store.go:30-121`), so a decorator
over `payment.Tx` records which books a unit of work touched with no plumbing.
Mesh tests then assert that the debtor bank's handler touched only its own book,
the CSM's only the network book, and the central bank's only the central-bank
book.

Those assertions **are** sub-project 8's specification, written before it starts.
Without them 7b ships a promise; with them, 8 is the mechanical extraction its
roadmap entry claims.

They mitigate rather than close. Method-level narrowing does not stop
`InitiatePaymentTx` from internally reading the creditor's book — which is
exactly why the debtor-half/creditor-half split above is load-bearing and not
merely tidy.

## What changes outside `mesh`

Collected here because the choreography above scatters it, and a plan needs one
list.

### `payment`

- **`Participant.BIC iso20022.BIC`** — new, as above.
- **`Payment.RejectCode iso20022.StatusReason`** — new, alongside the existing
  free-text `RejectReason`.
- **`payment/translate.go`** — new file. `Payment` → `pacs.008` / `pacs.003` /
  `pacs.004`, net positions → `pacs.009`, status → `pacs.002`, and back; plus
  the reason-code table. This is where `payment` starts importing `iso20022`.
- **`InitiatePaymentTx` splits** into the debtor half and the creditor half,
  with a submission entry point that picks one from `Scheme.Direction()`.
- **`SDD.Validate` splits** (`payment/scheme.go:143`): mandate at the creditor's
  bank, funds at the debtor's.
- **`RejectPaymentTx` splits** (`payment/system.go:1156`): the CSM's half and
  the debtor bank's half.
- `SettleCycleTx` and `ReturnPaymentTx` are **unchanged**. Only their callers
  move.

### `api`

- `POST /payments` on a bank: the bound-bank check becomes direction-aware
  (`handlers_bank_payment.go:86`), and the handler hands off to `mesh` instead
  of calling `InitiatePayment`. It still answers `202 Accepted` with
  `{paymentId}` — now genuinely asynchronous rather than merely shaped for it.
- `GET /payments/{payid}` on a bank **is** the status query. It already exists
  and 6a already shaped the web client around it, so nothing new is needed.
  Recording this because "`api/` moves to `202 Accepted` plus a status query"
  reads like two pieces of work and is one.
- `POST /cycles/{cid}/close` on the clearing house emits the `pacs.009`.
- `POST /settlements` on the central bank is **deleted**; the reserve and
  settlement reads stay.
- `/admin/reset` drains before truncating.

### `cmd/server`

`-entity` and its helpers go, as above. The mesh starts before the listeners;
the seed drains before `listening` is logged; shutdown drains, then stops.

### Stores

`bic` on `participants` and `reject_code` on `payments`, in `store/mem`,
`store/pg` (`0001_init.sql` plus `participantColumns`,
`store/pg/tx_payment.go:85`) and `store/storetest`. One migration file, as
always — nothing is deployed.

## Errors land in exactly three places

1. **Synchronous, at the submitting bank's API** — what that bank can see in its
   own books. Push: debtor account, asset, addressability, funds. Pull: creditor
   account, mandate. Unchanged 404/422 semantics.
2. **Asynchronous, as a `pacs.002 RJCT` plus a reason code** — what only the
   counterparty or the CSM can see: `AC01`, `AC04`, `RR01` from the creditor's
   bank; `AM04` from the debtor's bank on a pull and from the central bank on an
   uncoverable net position; `TM01` and `RC01` from the CSM.
3. **Dead letter** — nobody to tell. Returned, joined, by `Drain`.

`FF01` is both reachable and answerable: an unparseable envelope hides its own
header, but the queue knows which actor enqueued it, so the receiver can still
reply.

**`Payment.RejectCode iso20022.StatusReason`** joins the existing
`Payment.RejectReason string`, closing 7a's other open question (line 473).
Without it the code is computed and immediately thrown away, and a rejected
payment in the UI stays a free-text string when the entire point of the external
code sets is that a rejection is machine-actionable. Costs a `reject_code`
column in both stores and a `storetest` case.

### `OrgnlTxRef` stays unmodelled

7a deliberately did not model `OrgnlTxRef` on either `pacs.002` or `pacs.004`,
though the EPC guidelines make it mandatory on both — a ~20-field echo of the
original instruction, and the one identified respect in which this
repository's samples are an EPC subset. 7a asked 7b to revisit it if a
receiving bank ever had to reconstruct a rejected payment without having kept
state.

No receiver does. In hub-and-spoke the CSM is the actor that owns the payment
record — it writes every status transition — and it correlates each `pacs.002`
and `pacs.004` on `OrgnlEndToEndId`. A bank receiving a status report is being
told about a payment it submitted or was asked to accept, so it already has one.
The decision therefore stands, and the disclosure in `envelope.go` and
`testdata/README.md` stays accurate.

### The reason-code table

Lives in `payment/translate.go`, exactly as 7a decided (line 253), carrying 7a's
mapping unchanged. It is **exhaustive by construction**: a test parses
`payment/errors.go` with `go/parser`, enumerates every `Err*` sentinel, and fails
if one has no mapping. A new error becomes a test failure rather than a silent
`MS03` — which is the drift 7a named as a failure mode (line 454) and asked 7b
to close.

## Testing

`go test ./...` must stay green with no `DATABASE_URL` and against Postgres.
Both runs, as always.

- **Per-flow tests in `mesh`**: `Submit` → `Drain` → assert. No sleeps, no
  `Eventually`, no deadline on the happy path.
- **Book-access tests**, as above.
- **`FuzzTranslate`.** 7a's `FuzzUnmarshal` covers the parse boundary and found
  a real decode/encode asymmetry within ~24 seconds of first running. The new
  boundary is `translate.go`: fuzz a `Payment`, translate → marshal → unmarshal
  → translate back, assert equality.
- **A rolled-back handler sends nothing.** This pins the rule that no send
  happens inside a `Store.Update` — the property that matters, rather than the
  habit. A handler that enqueued while holding a transaction would schedule work
  against uncommitted state, or against state a rollback removed.
- **Deadlock**: a mutually-messaging pair drains rather than wedging.
- **Dead letters**: an injected malformed envelope surfaces through `Drain`.
- **`storetest`** gains cases for `Participant.BIC` and `Payment.RejectCode`.
  A one-value fixture is not a fixture — sub-project 5's review recorded that
  every identifier fixture holding exactly one identifier hid four distinct
  store divergences. These are scalars, so the equivalent trap is an empty
  string round-tripping identically through a store that drops the column
  entirely; the fixtures carry distinct non-empty values on every participant
  and every rejected payment.

**Cost to name now:** `api/server_test.go` has ~353 call sites, and every test
that submits a payment and then asserts on it must drain first. The harness
gains a mesh handle. Mechanical, but broad, and a plan should give it its own
task rather than smuggling it into another.

## Failure modes

- **The reject can half-happen.** Named in the choreography. It is the seam, not
  a bug to hide, and `Drain` surfaces it.
- **The boundary is a convention under a shared store.** Mitigated by the
  narrowed interfaces and the recorder — mitigated, not closed.
- **A wedged handler wedges `Drain`.** `Drain` takes a `ctx`; the timeout names
  the actor and the message.
- **`pacs.009` reopens `iso20022`**, which is done but unmerged. A new message
  file, `validate()`, a golden file, a registry entry and tests, landing on 7b's
  branch. It must follow 7a's existing group-header shape so that it adds no new
  inconsistency to the three EPC questions 7a recorded open (`Orgtr` as `PrvtId`,
  the `OrgnlEndToEndId`/`OrgnlTxId` one-of, and the EPC-mandatory group-header
  fields).
- **The mesh makes the test suite non-deterministic.** The whole `Drain` design
  exists to prevent this. If any test needs a sleep or a retry, that is the
  design failing, not the test being written badly.
- **`translate.go` drifts from the message structs.** `FuzzTranslate` plus the
  golden files are the cross-check.

## Out of scope

Listed in full so that what is possible after 7b is visible rather than
rediscovered.

### Already owned by a later sub-project

- **7c — the message log.** Envelopes persisted in both stores; a payment screen
  showing the XML that actually moved; the README, hint and quiz layers for it.
- **8 — per-entity stores.** Separate stores, and eventually separate databases,
  per entity. Plus `camt.054` and the unreconciled position — what makes
  "settlement is final, mirroring is not" visible. 8 stays *after* 7b: you
  cannot partition the tables until the choreography says who holds what, 8's
  actual deliverable is a `camt.054` and so needs a message layer to exist, and
  splitting first leaves the tree red across a whole sub-project because
  `SettleCycleTx` cannot compile against N stores until the mesh replaces it.

### The rest of the ISO 20022 family

- **`pain.001` / `pain.008`** — the customer-to-bank layer. A customer
  instruction is a JSON POST here; the real thing is a `pain.001` to their own
  bank, and the `pain` → `pacs` translation is a genuine second lesson.
- **`camt.052` / `camt.053` / `camt.054`** — account report, statement,
  debit/credit notification. There is already a statement screen to hang
  `camt.053` on.
- **`camt.056` / `pacs.007`** — recall and reversal: a *request* to return, as
  distinct from the return `pacs.004` already performs.
- **Runtime XSD validation.** `xmllint` remains an optional, offline golden-file
  test.
- **Message signing** (`Sgntr` in `head.001`).

### Transport and operational realism

- **Sockets instead of channels.** Buys separate processes back. The single
  `send` choke point is what keeps this contained.
- **Retries, timeouts, redelivery.** At-least-once plus an idempotent receive
  deduplicating on `BizMsgIdr`.
- **Durable queues.** A restart currently loses in-flight messages.
- **Bounded queues and backpressure.** A CSM that can be overwhelmed.

### Domain depth the mesh makes reachable for the first time

- **Batched bulks.** 7b sends one transaction per message, so `pacs.002`'s
  `GrpSts: PART` — which 7a deliberately built and this spec does not exercise —
  stays unused. Batching is what makes a partial rejection real.
- **Instant payments.** `payment/doc.go` already names this as next work and
  `SettlementModel` already has `Gross`. With a mesh it is `pacs.008` →
  immediate `pacs.009` per payment, with no cycle.
- **`pacs.028`**, a payment status request: a bank *asking* the CSM, rather than
  a UI polling a database row.
- **A cutoff timer.** Cycles close on an API call, never on a clock.
- **Liquidity management** — queueing a failed batch, unwinding a defaulter,
  extending intraday credit. `payment/doc.go:77` already names all three.
- **Debtor-side mandate records**, which would make `MD01` reachable on the wire.
  7b produces it only synchronously, at the creditor's bank.

### Staying non-goals

Authentication and authorization — the port is still the claim, per 6a. A real
BIC directory or SWIFT reference data. IBAN mod-97 validation, which
sub-project 5 decided against and whose absence the seed's readable IBANs
depend on.

## What 7c inherits

- Every message that moves is already a marshalled `iso20022.Envelope` passing
  through one function, which is the natural place to tee a log.
- `Payment.RejectCode`, so a stored rejection already names a code.
- `Participant.BIC`, so a logged envelope's `Fr`/`To` resolve to bank names.
- Two `README.md` bullets already corrected, leaving 7c the teaching layer
  rather than the corrections.
