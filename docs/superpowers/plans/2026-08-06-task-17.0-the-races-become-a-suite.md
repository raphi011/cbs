# Task 17.0 — the races become a suite

**Goal:** the nine race tests in `store/pg/pg_test.go` stop being one backend's
private tests. Four move into `store/storetest` and run on every backend; five
become re-instantiable against any backend that permits two transactions open at
once. Nothing about the domain changes.

**Why before 17.1, not after:** `store/pg` is deleted at 17.2 and `store/mem` at
17.3, and these nine tests go with the file. Three of Task 17's four money
defects were of the class these tests cover. A race test can only be *watched
failing* on a store with real MVCC — `store/mem` serialises, SQLite serialises
writers — so after 17.3 no race test written for this repository can be
demonstrated capable of failing. This task is the last point at which the
suite that certifies `store/sqlite` can itself be certified.

**Design:** `docs/superpowers/specs/2026-08-03-sqlite-only-store-design.md`
(sub-project 9) for what the swap does; this task is not in it and is an
addition to it, so record it there as a dated section when this lands. Method:
`docs/superpowers/2026-08-06-avoidable-review-cycles.md`, mechanism 3.

**Tech stack:** Go, no new dependencies. `store/mem` and `store/pg` both green,
as today.

## Global constraints

- **This plan carries no comment text.** Where a doc comment must make an
  argument, this plan names the argument in one line and the file it belongs in.
  Write the prose from the code you actually wrote. This is the convention
  change from the process file's mechanism 1 and it holds for every plan after
  this one.
- **Verify a correction's explanation as hard as the correction.** Never write
  down a measurement you did not take yourself, including one handed to you by a
  reviewer or a controller.
- **Every test moved is watched failing first, in its new home.** Break the code
  the test guards, watch that exact test fail with that exact message on
  `store/pg`, restore. A moved test that nobody has watched fail in its new
  package is an untested move — the barrier, the pool warmth and the store
  parameter are all things a move can silently break while the test still
  passes.
- **Never measure a store race on a cold connection pool.** `pgxpool` holds one
  idle connection after setup, so a second racer that is still opening TCP is
  not racing. The existing `barrier` is what pays this off inside a transaction;
  a race across units of work pays it by admitting one bank before the racers
  start. Where neither applies, warm the pool explicitly.
- **A guard that cannot fail is not a guard.** For each of the four shared
  races, record whether it is capable of failing on `store/mem` at all. Most are
  not, and that is the conformance claim rather than a defect — but it must be
  written down per test, because at 17.1 the same question is asked of SQLite
  and the answer there is not known yet.
- **Both stores.** `go test ./...` runs on `store/mem`;
  `TEST_DATABASE_URL=… go test ./...` runs the same suites on `store/pg`.
  `make test-pg` uses Docker and does not work on this machine — use the
  explicit invocation. The Postgres run takes 20–39s on the store-touching
  packages against 1–5s on `store/mem`; a fast run skipped, and a skip is not a
  pass.
- **No domain change.** Not one accept-or-refuse decision moves. If an assertion
  has to change to make a test pass in its new home, that is a defect in the
  move until proven otherwise.

## The split, and why it is 4 and 5

`raceInTransactions` opens `n` units of work and holds a barrier **inside** the
transaction: no racer issues its first statement until every racer has begun.
`store/mem` admits one `Update` at a time, so the second racer cannot reach the
barrier and the test hangs rather than fails. Five races use it and none of them
can be shared with `store/mem`.

`runConcurrently` races whole units of work against each other. Four races use
it — the four that drive `payment`'s acts — and they run on any backend.

| test | driver | new home |
|---|---|---|
| `TestConcurrentAdmissionsAgreeOnOneCentralBank` | `runConcurrently` | `storetest.RunRaces` |
| `TestConcurrentSubmissionsOfOneReferenceAcceptOne` | `runConcurrently` | `storetest.RunRaces` |
| `TestConcurrentAdmissionsOfOneBICAdmitOne` | `runConcurrently` | `storetest.RunRaces` |
| `TestConcurrentSettlementAccountOpeningsKeepEveryAsset` | `runConcurrently` | `storetest.RunRaces` |
| `TestConcurrentPostingsCannotBothSpendTheSameBalance` | `raceInTransactions` | `storetest.RunConcurrentTxRaces` |
| `TestConcurrentPostsWithOneIdempotencyKeyCollide` | `raceInTransactions` | `storetest.RunConcurrentTxRaces` |
| `TestConcurrentPutTransactionWithOneIdempotencyKey` | `raceInTransactions` | `storetest.RunConcurrentTxRaces` |
| `TestConcurrentMarkReversedOnlyOneWins` | `raceInTransactions` | `storetest.RunConcurrentTxRaces` |
| `TestOverlappingAccountSetsDoNotDeadlock` | `raceInTransactions` | `storetest.RunConcurrentTxRaces` |

Two entry points, not one. `RunRaces` is called by every backend and is a
conformance claim: the stores agree on who wins. `RunConcurrentTxRaces` is
called only by a backend that permits two transactions open at once, and
`store/mem` does not call it. The split is a property of the store, so the
choice is the backend's own test file — not a skip inside the suite, which would
report PASS for a suite that never ran.

## The question this task hands to 17.1

`RunConcurrentTxRaces` asserts, through `assertOneWinner`, that every loser
fails with a **domain sentinel** — `ledger.ErrInsufficientBalance`,
`ledger.ErrDuplicateIdempotencyKey`. Under SQLite two transactions can both
`BEGIN` (deferred takes no lock), so the barrier releases, and the second to
write gets `SQLITE_BUSY` on the write-upgrade. `busy_timeout` cannot absorb a
conflict whose holder is still open, so the loser's error is a busy error and
not the sentinel — and `assertOneWinner` fails on the reason rather than the
count.

The spec says these codes are "mostly absorbed by `busy_timeout`". That is the
claim 17.1 has to establish or reverse, and after this task it has five tests
that ask the question directly instead of a prediction in a design document.
Do not resolve it here.
